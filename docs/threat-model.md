# Threat model

This is a STRIDE threat model of the places where Toolkit's code or releases cross a trust boundary. It is the source of truth for accepted residual risks.

Each boundary lists its assets and actors, then a table with one row per threat. The STRIDE category is the letter before the threat: **S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service, **E**levation of privilege. Residual risks decided by the maintainer on 2026-09-29 in PR #158.

Terms follow the package glossaries: [toolkit-sync](../packages/toolkit-sync/CONTEXT.md) (Baseline, Signed release tag, Trust anchor, Legacy tag) and [security-gates](../packages/security-gates/CONTEXT.md) (Gate, Core Gate, Caller workflow, Starter configuration, Suppression).

## Keeping this model current

A pull request that changes a trust boundary updates this model in the same pull request (see [CONTRIBUTING](../CONTRIBUTING.md#pull-requests)). Trust boundaries include workflow permissions, the release process, vendoring, hooks, and what reaches consumers. A row's mitigation must link a file, setting, issue or pull request that exists on `main`.

Some mitigations are repository settings rather than files. These values were read with `gh api` on 2026-09-29. The links marked "admin" need admin access to read.

## 1. Release and tags

**Assets:** the `main` branch, the `vX.Y.Z` tags, the release tag signing key, and each GitHub Release's source archive, `SHA256SUMS`, SBOM and build provenance attestation.

**Actors:** the maintainer, who is the only code owner; the workflow `GITHUB_TOKEN`, acting as `github-actions[bot]`; Dependabot; contributors from forks; and the third-party actions and tools the workflows run.

The release flow is in [docs/release.md](release.md). [Prepare release](../.github/workflows/prepare-release.yml) rebuilds the `release/next` pull request after each merge. On every push to `main`, [Publish release tag](../.github/workflows/publish-release.yml) runs a read-only `detect` job, and only a merge of the `release/next` pull request reaches the `tag` job. The design is in [ADR 0002](adr/0002-toolkit-sync-verifies-ssh-signed-release-tags.md), with the implementation in [#155](https://github.com/ClabonConsultingLtd/Toolkit/issues/155) and [PR #156](https://github.com/ClabonConsultingLtd/Toolkit/pull/156).

| Threat | Current mitigation | Residual risk | Follow-up |
| --- | --- | --- | --- |
| **R1.1** (S, T) An unreviewed change reaches `main`, for example from a stolen contributor token. | S1: every change goes through a pull request with a code owner's review and the required checks. No force push or deletion is allowed. | Toolkit has one maintainer, who can't approve their own pull request, so the maintainer merges without a second reviewer. A compromised maintainer account can merge anything, and can also change the rulesets. Accepted because Toolkit has one maintainer, every merge is still a public pull request, and toolkit-sync's tag-move detection (R2.4) still protects existing pins. | Add a second reviewer if one joins the project. |
| **R1.2** (T) A published `v*` tag is moved or deleted to point consumers at other code. | S2 blocks deleting, updating or force-pushing `v*` tags, with no bypass. S4 locks a published Release's tag. toolkit-sync records each pin's commit SHA and refuses to go on if the tag moves (R2.4). | Only an administrator who disables the ruleset could move a tag. Accepted because that is the account compromise in R1.1, and toolkit-sync still detects the move for existing pins. | None. |
| **R1.3** (S, D) A new `v*` tag is created outside the publish workflow. | Since v0.14.0, toolkit-sync rejects an unsigned tag at or above `FIRST_SIGNED_VERSION` in [`signature.mjs`](../packages/toolkit-sync/src/signature.mjs), and `--allow-unsigned` doesn't apply there. The `tag` job never moves an existing tag, and it verifies the tag before pushing, so a squatted unsigned tag fails the release instead of being published. | S2 doesn't restrict creating tags. The maintainer, or a compromised step in any job with `contents: write`, could create a tag in the Legacy tag range (an unused version below v0.14.0). A consumer passing `--allow-unsigned` would accept it. A squatted future version also blocks that release, because the tag can't be deleted. Accepted until #159 lands: creating such a tag needs write access or a compromised privileged job, and `--allow-unsigned` is off by default. | [#159](https://github.com/ClabonConsultingLtd/Toolkit/issues/159): make toolkit-sync accept only the known Legacy tags, by shipping their names and commit SHAs as a fixed list next to `FIRST_SIGNED_VERSION`. Consider a tag-creation rule in S2 that still lets the publish workflow create tags. |
| **R1.4** (E, S) A compromised release workflow signs attacker-chosen content. ADR 0002 names this residual risk. | The key is an environment secret in `release` (S3), and only `main` may deploy there. Only the `tag` job uses the environment, and it runs only when the read-only `detect` job ([`release-merge.mjs`](../.github/scripts/release-merge.mjs)) finds a merged `release/next` pull request from this repository, based on `main`, whose merge commit is the pushed SHA. The key is written to a `0600` temporary file, only when the tag is new, and deleted by a trap and an `if: always()` step. Workflow changes go through S1 review, actions are SHA-pinned (S5), and [zizmor](../.github/workflows/verify.yml) lints every workflow. [`prepare-release.test.mjs`](../.github/scripts/prepare-release.test.mjs) checks the workflow's shape. | The key lives in CI, so a compromised release workflow can still sign. A merged workflow change that declares `environment: release` on a push to `main`, a compromised pinned action or runner, or a compromised step in the `tag` job before the key is deleted can read the key or sign any tag. Every consumer would accept that signature. S3 has no required reviewer, and administrators can bypass its rules. Accepted because ADR 0002 chose a key held in CI to keep toolkit-sync free of host APIs, and every workflow change is a reviewed public pull request. | Add a required reviewer to the `release` environment, so each signing run waits for the maintainer's approval, and turn off administrator bypass. |
| **R1.5** (S) A stolen signing key signs a release that keeps itself trusted. ADR 0002 names this residual risk. | The key is used only in the `tag` job (R1.4). The [toolkit-sync README](../packages/toolkit-sync/README.md#key-compromise) documents recovery: a security advisory published outside the release channel, then a manual replacement of the Trust anchor. Planned rotation ships both keys, with `valid-before` on the old one. S9 gives reporters a private channel. | A `sync` can't recover from a compromise, because the stolen key can sign a release whose Trust anchor still trusts it. Consumers are protected only once they read the advisory and replace the Trust anchor by hand. Accepted because ADR 0002 accepted it as the cost of a long-lived key. | Say in [SECURITY.md](../SECURITY.md) where a key-compromise advisory would be published, so consumers know where to watch. |
| **R1.6** (T) A pull request adds an attacker's key to the Trust anchor, `packages/toolkit-sync/allowed_signers`. | S1 review. The `tag` job verifies its own tag against the Trust anchor in the checked-out tree, so replacing the release key breaks the release rather than shipping. When `sync` would write toolkit-sync's Trust anchor, it compares the consumer's vendored copy with the release's as normalised entries (principal, options and key), so formatting doesn't count, and prints every added and removed entry as principal and SHA256 fingerprint ([`trust-anchor.mjs`](../packages/toolkit-sync/src/trust-anchor.mjs)). Any added entry, including a known key under a new principal or new options, stops that package's sync, which writes nothing until `--accept-trust-anchor-change` is passed. `--force` doesn't bypass it, and a destination with no anchor counts as every entry added. `check` reports the same change and fails on an addition. The [`toolkit-upgrade` skill](../packages/toolkit-sync/claude/skills/toolkit-upgrade/SKILL.md) tells agents to show the user the keys and pass the flag only when the user agrees. | An added key, kept alongside the release key, can still pass Toolkit's review. A consumer that accepts the change without checking the fingerprint then trusts the key for every later sync. Accepted because the key can no longer arrive silently: each consumer sees its fingerprint and must opt in. Removals, as in a planned key rotation, are printed but need no flag. | None. |
| **R1.7** (T) Release assets are swapped or the archive doesn't match the tag. | S4 makes published assets immutable. The `tag` job builds the archive from the tag, publishes `SHA256SUMS` and an SBOM, and attests build provenance. [docs/release.md](release.md#verifying-a-release) shows how to check both. Syft is pinned by version and SHA-256. | Checking the archive is manual. Accepted because toolkit-sync takes code from git and verifies the tag, not the archive, so the archive is a convenience. | None. |
| **R1.8** (T) Someone tampers with the release candidate on `release/next`. | [Prepare release](../.github/workflows/prepare-release.yml) rebuilds `release/next` from `main` after every merge, discarding hand edits. The release pull request is reviewed and merged under S1. `detect` rejects a `release/next` from a fork or with another base. | The release pull request is bot-authored, so its diff relies on the maintainer's review. Accepted because it only changes versions, lockfiles and `CHANGELOG.md`, which the maintainer reviews before merging. | None. |
| **R1.9** (R) The origin of a release can't be traced. | The Signed release tag names the `toolkit-release` principal, and toolkit-sync records it as `signer` in the pin file. The provenance attestation ties the archive to the workflow run. Merges are public pull requests. | The tagger is `github-actions[bot]`, not a person. Accepted because the run, the merged pull request and the attestation identify who released it. | None. |
| **R1.10** (I) The signing key leaks through logs or artifacts. | Only the signing step gets the secret, as an environment variable. It is written with `printf` to a `0600` file and never echoed, and the `${{ }}` expressions stay out of `run:`. GitHub masks secret values in logs. No artifact is uploaded from the `tag` job. | A later step can't read the deleted file, but GitHub's log masking is the backstop against an accidental echo. Accepted because the step is short, reviewed and linted by zizmor. | None. |
| **R1.11** (I) Private details from a consumer repository are published in this public repository. | [verify.yml](../.github/workflows/verify.yml) fails when files, commit messages or the pull request's branch, title or body contain a private term. The terms are kept in a secret, not in the workflow. [private-term-watch.yml](../.github/workflows/private-term-watch.yml) redacts issue, pull request and comment text as it's posted. S8 secret scanning with push protection and the secrets Gate cover credentials. | The check only catches terms on the list, and a redaction still leaves the original in GitHub's edit history. Accepted because [CONTRIBUTING](../CONTRIBUTING.md#before-changing-code) already forbids project-specific paths and infrastructure names, so the check is a backstop. | None. |
| **R1.12** (E) A compromised third-party action or tool runs with a write token. | S5 requires full-SHA pins, and [Dependabot](../.github/dependabot.yml) proposes weekly action bumps as reviewed pull requests. Every workflow defaults to `contents: read` and grants writes per job. S6 makes the default token read-only. zizmor runs in `verify`. S7 holds fork workflows for approval. | S5 allows any action, not an allow list. Toolkit's own Dependabot action updates have no cooldown, unlike the Starter configuration's seven days. Accepted until #162 lands: every bump is reviewed and SHA-pinned. | [#162](https://github.com/ClabonConsultingLtd/Toolkit/issues/162): restrict the allowed actions, and add a `cooldown` to the `github-actions` entry in `.github/dependabot.yml`. |
| **R1.13** (E) A workflow approves its own pull request. | S1 requires a code owner's review, and `github-actions[bot]` isn't a code owner. | S6 lets Actions create and approve pull requests. Prepare release and the scanner bump need that to open their pull requests. Accepted because a bot approval can't satisfy the code owner review. | None. |

## 2. Vendoring with toolkit-sync

**Assets:** a consumer repository's vendored files, its `toolkit-pins.json` (pins, `signer` and each package's Baseline), and its copy of the Trust anchor.

**Actors:** the consumer's maintainers, and agents following the `toolkit-upgrade` skill; the Toolkit remote, or another remote given with `--repo`; the network in between; and anyone who can publish a tag.

toolkit-sync is described in its [README](../packages/toolkit-sync/README.md). Signing began with [#152](https://github.com/ClabonConsultingLtd/Toolkit/issues/152) and ADR 0002. v0.14.0 is the first Signed release tag. On 2026-09-29 it verified against the Trust anchor, and every earlier tag is a Legacy tag.

| Threat | Current mitigation | Residual risk | Follow-up |
| --- | --- | --- | --- |
| **R2.1** (S) A tag that the publish workflow didn't make is pinned, from a fork, a mirror given with `--repo`, or an attacker on the network. | `pin`, `check` and `sync` run `git verify-tag` against the Trust anchor before trusting a commit, and fail closed ([`signature.mjs`](../packages/toolkit-sync/src/signature.mjs)). Success needs a zero exit and a named principal. A tag object republished under another tag's name is rejected. The default remote is HTTPS. | None beyond the signing key risks in R1.4 and R1.5. Accepted because those rows cover the key. | None. |
| **R2.2** (S) `--allow-unsigned` accepts a Legacy tag without verification. | Legacy tags are refused by default, and the flag prints a warning. It never applies at or above v0.14.0. Existing Legacy tags can't move (S2), and each pin's commit SHA is checked on every command. The [`toolkit-upgrade` skill](../packages/toolkit-sync/claude/skills/toolkit-upgrade/SKILL.md) tells agents to use the flag only for Legacy tags, with the user's agreement. | A consumer pinned to a Legacy tag passes the flag on every command, and a new tag created in the Legacy tag range would be accepted too (R1.3). Accepted until #159 lands: the flag is explicit and each consumer leaves the Legacy tag range at its next upgrade. | [#159](https://github.com/ClabonConsultingLtd/Toolkit/issues/159): the fixed Legacy tag list from R1.3. |
| **R2.3** (S) The first copy of toolkit-sync, and its Trust anchor, comes from an attacker. | The README says to check the first verifying upgrade's tag by hand with the new Trust anchor. The key's fingerprint is in [#154](https://github.com/ClabonConsultingLtd/Toolkit/issues/154) and [PR #156](https://github.com/ClabonConsultingLtd/Toolkit/pull/156). | The first copy of the tool and its Trust anchor arrives through the channel it protects, so it is trusted on first use. Accepted because it's a one-time step that the README calls out. | Publish the key's fingerprint outside the release channel, so first use can be checked against a second source. |
| **R2.4** (T) A tag moves after a consumer pinned it. | The pin file records the tag's commit SHA. `check` and `sync` re-fetch the tag and refuse if it now names another commit. S2 blocks the move upstream. | None. Accepted. | None. |
| **R2.5** (T) A `sync` silently overwrites a local edit, or hides one inside an upstream change. | The Baseline records the commit, file list and SHA-256 of each file `sync` last wrote ([`package-sync.mjs`](../packages/toolkit-sync/src/package-sync.mjs)). `check` labels each difference, and `sync` refuses `local-edit` and `modified` files without `--force`. | `--force` overwrites everything it lists, and anyone who can commit to the consumer repository can edit the Baseline. Accepted because both are explicit acts inside the consumer's own review. | None. |
| **R2.6** (T) The Trust anchor is edited in the consumer repository. | No toolkit-sync code path writes the Trust anchor except a verified `sync` of the toolkit-sync package, which needs `--accept-trust-anchor-change` to add a key (R1.6). `allowed_signers` is in [the package manifest](../packages/toolkit-sync/toolkit-manifest.json), so if toolkit-sync is itself pinned, `check` reports an edit as `local-edit`. | A consumer that doesn't pin toolkit-sync itself gets no report of an edited Trust anchor. Accepted because such an edit is a change in the consumer's own reviewed history. | Recommend in the toolkit-sync README that consumers pin toolkit-sync itself. |
| **R2.7** (T) A consumer is moved back to an older Signed release tag with a known flaw. | The consumer chooses each tag, and the pin file change goes through the consumer's review. | toolkit-sync doesn't refuse a downgrade. Accepted because choosing a version is the consumer's decision. | None. |
| **R2.8** (T) Files are written outside the package's directory. | `pin --dest` must be inside `--cwd` ([`cli.mjs`](../packages/toolkit-sync/src/cli.mjs)). Files come from the pinned commit's git tree, filtered by the package's `toolkit-manifest.json`. | A `--dest` passed to `check` or `sync`, or a hand-edited `dest` in the pin file, isn't confined to `--cwd`. Accepted because both come from the person running the command. | None. |
| **R2.9** (D) The remote is unavailable, or a tag can't be verified. | toolkit-sync fails closed and writes nothing. It needs only git and `ssh-keygen`, with no host API. | Upgrades wait until the remote or a valid tag is back. Accepted because failing closed is the intended behaviour. | None. |
| **R2.10** (E) More code reaches consumers than the package intends. | Each package's `toolkit-manifest.json` lists what is vendored as explicit globs. Tests and lockfiles are excluded. | Vendored code runs with the consumer's privileges, which boundaries 4 and 5 cover. Accepted. | None. |

## 3. security-gates as called by consumers

**Assets:** a consumer's CI result, its workflow token and code scanning alerts, and the scanner binaries, rules and scripts the Gates run.

**Actors:** the consumer's Caller workflow; Toolkit's [reusable workflow](../.github/workflows/security-gates.yml); scanner publishers; the [scanner bump workflow](../.github/workflows/security-gates-scanner-bump.yml); and authors of pull requests in the consumer repository, whose content the Gates read.

[ADR 0001](adr/0001-security-gates-called-not-vendored.md) explains why the Gates are called, not vendored.

| Threat | Current mitigation | Residual risk | Follow-up |
| --- | --- | --- | --- |
| **R3.1** (T) A consumer runs Gate code other than what it reviewed. | The [Starter configuration](../packages/security-gates/starter/security-gates.yml)'s Caller workflow pins a commit SHA. The [adoption steps](../packages/security-gates/README.md#adoption) copy that SHA from `toolkit-pins.json`, which toolkit-sync verified. Every Gate job checks out the Gate scripts, rules and `scanner-versions.json` at `job.workflow_sha`, the same commit the Caller workflow called. | Dependabot bumps the pinned SHA to a new release's commit without checking the tag's signature. Accepted because each bump is a reviewed pull request in the consumer repository, the Starter configuration waits seven days before proposing it, and S2 stops the tag moving. | None. |
| **R3.2** (T) A scanner binary is tampered with in transit or at its download host. | [`install-scanners.mjs`](../packages/security-gates/scripts/install-scanners.mjs) checks each download's SHA-256 against [`scanner-versions.json`](../packages/security-gates/scanner-versions.json). For Trivy and Dockle the pin must also match the release's checksums file, and Opengrep's and Trivy's cosign signatures are verified. cosign is installed the same way. | None beyond R3.3. Accepted. | None. |
| **R3.3** (T, E) A compromised scanner release enters through a version bump. | The bump workflow is split. `verify-bump` has `contents: read` and `persist-credentials: false`, and it downloads, verifies and runs the new scanners. `open-pr` holds the write token but only checks the versions file's shape with [`validate-versions.mjs`](../packages/security-gates/scripts/validate-versions.mjs), so it never runs a scanner. The bump is a reviewed pull request. | Verification proves only that a download matches what the publisher released, not that the publisher wasn't compromised. The bump pull request is labelled `release:patch`, so once merged it ships in the next release. The workflow's own comment says CI doesn't run on it until the maintainer reopens it. Accepted because a person reviews and merges every bump, and consumers get it only through their own reviewed pin bump. | None. |
| **R3.4** (E) Attacker-controlled pull request content exploits a scanner. | Every Gate job has `contents: read`, and both checkouts use `persist-credentials: false`. The reusable workflow takes no secrets. Only the code scanning upload job inherits the Caller workflow's `security-events: write` and `actions: read`, and it runs no scanner. | A scanner exploit would run with the consumer's read-only token and could falsify its own Gate's result. Accepted because the token can't write, and pull requests still need the consumer's review. | None. |
| **R3.5** (T) A finding is hidden by a Suppression. | A Suppression lives in the consumer's own ignore file. Each Gate fails when a Suppression has no reason, no expiry or a past expiry ([`check-suppressions.mjs`](../packages/security-gates/scripts/check-suppressions.mjs)). | Whether a Suppression is justified is the consumer's review decision. Accepted because Toolkit never writes a Suppression (ADR 0001). | None. |
| **R3.6** (D, T) The Gates are skipped or made optional. | No input can switch off a Core Gate. The [README](../packages/security-gates/README.md#adoption) tells consumers to make the three Core Gates required checks. | Toolkit can't enforce a consumer's branch rules. Accepted because branch rules are the consumer's setting. | None. |
| **R3.7** (E) The Gates get more permission than they need. | A reusable workflow's jobs get at most what the Caller workflow grants, and the Starter configuration grants only `contents: read`. The [README](../packages/security-gates/README.md#permissions) explains the two extra permissions that code scanning needs. | None. Accepted. | None. |

## 4. Agent hooks and scripts in consumer agent sessions

**Assets:** the consumer's working tree, its credentials, and the agent session's permission decisions.

**Actors:** coding agents such as Claude Code and Codex; the consumer who installs the hooks and skills; and authors of issue and comment text that agents read.

The Toolkit parts are the [`claude-token-optimisation`](../packages/claude-token-optimisation/README.md) hooks and the [`agent-workflow`](../packages/agent-workflow/README.md) scripts and skills.

| Threat | Current mitigation | Residual risk | Follow-up |
| --- | --- | --- | --- |
| **R4.1** (E) The Bash summary hook runs a command outside the agent's permission prompt. | [`summarize-bash.mjs`](../packages/claude-token-optimisation/hooks/summarize-bash.mjs) runs a command only if [`command-summary.mjs`](../packages/claude-token-optimisation/hooks/command-summary.mjs) matches it to a short allowlist: `git status`, a dependency listing, one Vitest file, and a type check. The prefixes and suffixes it allows (`cd`, `timeout`, `set -o pipefail`, a trailing `tail` or `head`) are matched strictly, and quoted `cd` paths can't hold `` ` ``, `$` or `\`. [Tests](../packages/claude-token-optimisation/test/command-summary.test.mjs) reject `;`, `$(…)`, `&&` and pipes. Subagent and background commands pass through. | The hook runs an allowlisted command through a shell, and then denies the original call. That means Claude Code's permission prompt never sees it. Vitest and the type check execute the project's own code. Accepted because the allowlist covers only the project's own tests, type check and read-only commands, which a session is expected to run. | Say in the package README that the hook runs allowlisted commands itself, without the agent's permission prompt. |
| **R4.2** (I) Full command output kept by the hook leaks. | The output is written under the project's `.toolkit` state directory, which [docs/security.md](security.md) says belongs outside source control. | The log files are created with default permissions and aren't redacted. Accepted because they hold only what the command printed to the same user's session. | None. |
| **R4.3** (T) `install.mjs` changes a consumer's agent settings unexpectedly. | [`install.mjs`](../packages/claude-token-optimisation/install.mjs) copies the hook files, writes an example settings file only if it's absent, and never merges hooks into `settings.json`. It only rewrites older entries for its own two hooks. | It overwrites its own hook files without asking. Accepted because those files are Toolkit's, and the consumer runs the installer. | None. |
| **R4.4** (I, T) Model handoff sends code to a remote model, or applies edits outside its task. | Handoff is off unless `TOOLKIT_HANDOFF_ENABLED=on` ([`handoff.mjs`](../packages/agent-workflow/src/handoff.mjs)). Remote endpoints must use HTTPS. Files must be declared in the task file and stay inside the root, and symlinks are refused ([`task-file.mjs`](../packages/agent-workflow/src/task-file.mjs)). An edit to an undeclared file is rejected, and edits apply atomically ([`blocks.mjs`](../packages/agent-workflow/src/blocks.mjs)). The API key isn't logged. | The declared files are sent to the configured provider. Accepted because enabling handoff and choosing the endpoint are explicit consumer decisions, and [docs/security.md](security.md) says to review every applied diff. | None. |
| **R4.5** (E) The ticket launcher runs ticket content as a command. | [`ticket-launch.mjs`](../packages/agent-workflow/src/ticket-launch.mjs) runs the consumer's configured command without a shell, and passes only the ticket reference as one argument. A [test](../packages/agent-workflow/test/ticket-launch.test.mjs) shows `$(…)` in a ticket path isn't executed. | The launched command and its permission mode are whatever the consumer configures. Accepted because Toolkit supplies no default command. | None. |
| **R4.6** (E, T) Issue or comment text steers an agent (prompt injection). | The [triage-tickets skill](../packages/agent-workflow/claude/skills/triage-tickets/SKILL.md#trust-boundary) never runs anything a reporter supplied, and never launches an implementation agent. Its [protocol](../packages/agent-workflow/claude/skills/triage-tickets/references/protocol.md) passes arguments separately and never puts issue text into commands. Two checks in [`orchestration-github.mjs`](../packages/agent-workflow/src/orchestration-github.mjs) run before selection and before reservation, so they don't depend on the model. A ticket starts only with a brief whose author's `authorAssociation` is `OWNER`, `MEMBER` or `COLLABORATOR`, or when such an author opened the issue. Accepted because only trusted authors define the task, text changed after approval never starts, and merges still need branch protection to pass. | None. |

## 5. Image packages

**Assets:** the consumer's Hugging Face token, source images, and generated outputs.

**Actors:** the consumer running the CLIs; a third-party Hugging Face Space; and the runner executable the caller supplies.

The packages are [`image-generation`](../packages/image-generation/README.md) and [`image-to-3d`](../packages/image-to-3d/README.md).

| Threat | Current mitigation | Residual risk | Follow-up |
